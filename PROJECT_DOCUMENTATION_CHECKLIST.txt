PROJECT OBJECTIVES AND MODULES
------------------------------
The prototype addresses four stated pain points:
- Enrollment queues: student applications and status review are represented as
  an online submission/review workflow.
- Clearance: the API tracks cashier, library, department, dean, guidance, and
  registrar sign-offs and derives pending/cleared status.
- Grade viewing: assigned faculty can enter grades; students are restricted to
  their own eligible records and see grades only after explicit release.
- Document requests: students submit requests and follow payment/processing/
  pickup/release states. Payment is simulated; no payment gateway or document
  production service is integrated.

Modules currently present in source:
- Student Portal: registration, application, progress/clearance, sections,
  released grades, and document requests.
- Registrar: application queue/review, student registry, grade release, and
  document fulfillment actions.
- Cashier: payment-state updates and cashier clearance sign-off.
- Department: department/dean clearance, course/section oversight, and
  department-scoped academic workflows.
- Faculty: assigned section roster and grade entry/release.
- Admin: metrics, user management, course catalog maintenance, and broader
  administrative API actions.
- Document Request System: separate student request and staff payment and
  fulfillment workflow.

TASK 2: SYSTEM MODELING
----------------------
Create diagrams with a consistent system boundary, role names, data stores, and
arrows/labels. Give each diagram a title, legend if needed, and short paragraph
explaining its key decisions. Diagrams must agree with the implemented workflows
and the paper; Mermaid drafts can be used, but render and inspect them before
submission.

A. Data Flow Diagram (DFD)
Show external entities (Student, Registrar, Cashier, Department/Dean, Faculty,
Administrator), major processes (application review, section enrollment,
clearance, grade handling, document fulfillment), and data stores (users,
students, applications, sections/rosters, enrollments/grades, clearances,
document requests). Label important flows and distinguish external actors from
internal processes. A context diagram plus Level 1 decomposition is useful.

B. Use Case Diagram
Show the system boundary and actors with their permitted goals: register/sign
in, submit application, review application, manage section/roster, update
clearance, enter/release grades, request/fulfill documents, and administer
accounts/catalog. Use include/extend only where there is a real dependency.
Check actor permissions against `api/routes/api.php` and controller checks.

C. Activity Diagram
Show at least one complete high-value workflow, with start/end, decisions,
rejections/error branches, and role handoffs. Recommended: student application
-> registrar review -> approval/rejection -> clearance -> section enrollment.
A second diagram may show document request -> payment -> processing -> release.

D. Class Diagram
Show the core domain classes, key attributes, relationships and multiplicity:
User, Student, StudentApplication, Course, AcademicSection,
SectionEnrollment, Enrollment, Clearance, DocumentRequest, ApiAccessToken.
Align this with Laravel models and migrations. Do not imply classes, constraints,
or behaviors that do not exist in code.

TASK 3: SYSTEM DESIGN
---------------------
A. UI/UX storyboard and wireframes
Provide a storyboard that follows a named user goal from screen to screen, plus
wireframes for login/registration and the role dashboards. Include mobile and
desktop views, important empty/loading/error/success states, form validation,
navigation, and accessible keyboard/focus behavior. Explain why each control
supports the actor's task. Capture actual prototype screens if possible and
caption them; do not represent mockups as implemented screens.

Current evidence: Vue components exist for the public landing/login, shared
navigation, error/toast/modal patterns, and role-specific dashboards. A set of
screenshots and complete accessibility/responsive certification are not
provided by this text file.

B. Database design, ERD and/or 3NF
Draw primary keys, foreign keys, cardinalities, junction table, and important
uniqueness constraints. Explain normalization to 1NF, 2NF, and 3NF using the
actual schema and functional dependencies; do not merely state "3NF". Include
all core entities and explain why `SectionEnrollment` represents the
student-section many-to-many relationship while `Enrollment` stores a student's
academic result for a course/term. Match table and column names to migrations.
Identify denormalized/duplicated fields and justify or propose corrections
without claiming they are already corrected.

TASK 4: SOFTWARE TESTING PLAN
-----------------------------
For every test case record an ID, level, requirement, preconditions, test data,
steps, expected result, actual result, pass/fail, date, and tester. Keep test
accounts/data synthetic. Separate planned tests from tests actually run.

A. Unit testing
Test isolated calculation/validation behavior, such as grade average and
allowed grade bounds, document fee calculations, valid status transitions, and
role-rule helpers. Existing Laravel files include a placeholder/example unit
test; do not overstate it as comprehensive unit coverage.

B. Integration testing
Test API + database interactions and relationships: application review creates
or updates the expected student/clearance state; section enrollment creates one
roster/enrollment record; grade release changes student visibility; payment and
document transitions persist. Existing `PortalWorkflowTest` covers several
cross-controller lifecycle paths using Laravel's test environment.

C. System testing
Exercise the composed frontend, API, PostgreSQL, and Redis services together:
startup/health, sign-in, role dashboard data, denial paths, workflows, restart,
and persistence. Record browser, viewport, Compose version, logs, and results.
A frontend build or a backend test alone is not full system testing.

D. Acceptance testing
Have representative student and staff users execute acceptance criteria for
realistic scenarios. Record sign-off and defects. Include mobile/keyboard use,
role boundaries, clear error recovery, and stakeholder confirmation that policy
matches the institution. Automated feature tests are not stakeholder acceptance.

E. Performance testing
Define expected concurrent users, response-time targets, data volume, and
hardware/environment first. Then exercise representative read/write endpoints
and peak workflows with a named load tool; measure latency percentiles, error
rate, throughput, CPU/memory, and database behavior. The codebase has no
performance/load-test evidence; do not invent results.

F. Security testing: at least three vulnerabilities and controls
1. SQL injection: use Laravel query builder/Eloquent parameter binding; validate
   input, avoid concatenating raw SQL, and test malicious search/filter values.
2. Brute-force login: apply rate limits to login and registration; test repeated
   failures, lockout/throttle behavior, logging, and recovery. The routes have
   named throttle middleware, but production threshold/configuration and
   monitoring still require verification.
3. Broken access control / IDOR: enforce role and record ownership on every API
   request, not only in the UI; test cross-student IDs, unauthorized role
   actions, faculty outside assigned sections, and inactive/expired tokens.
4. Credential/session exposure: hash passwords and stored bearer tokens, use
   HTTPS, expire/revoke tokens, protect browser storage against XSS, rotate
   production secrets, and never commit `.env` files or demo credentials.
5. CORS/configuration errors: allow only the intended frontend origin in
   production; test preflight and disallowed origins. CORS is not authentication.

Use approved tooling and an isolated test/staging environment. Include test
scope, findings, severity, remediation, retest evidence, and residual risk. Do
not test production systems without authorization.

TASK 5: ETHICAL EVALUATION
--------------------------
Evaluate the system against the ethical principles taught in the course and the
applicable institutional policies/law. At minimum discuss:
- Privacy and confidentiality: student records are sensitive; minimize data,
  restrict access, define purpose, retention, deletion, breach response, and
  secure backups.
- Fairness and non-discrimination: assess consistent access and treatment for
  all student lifecycle categories and users with disabilities or limited
  connectivity; review automated decisions for bias.
- Transparency and informed participation: explain what data is collected,
  why, who can see it, how grades/statuses are decided, and how to request
  correction or appeal.
- Accountability: identify the office/person responsible for each approval,
  error correction, audit trail, and incident response. Current app logs some
  admin changes but is not a complete institutional audit system.
- Accessibility and inclusion: evaluate keyboard operation, contrast, labels,
  screen-reader semantics, responsive behavior, language, and low-bandwidth use.
- Accuracy and harm prevention: prevent fake/demo grades, stale status, or
  incorrect fees from being mistaken for official records. This prototype's
  seeded data and payment/document workflows must be clearly labeled.
- Professional integrity: distinguish implemented features from proposed work;
  disclose limitations and cite sources ethically.

The paper should present evidence, impact, mitigations, residual concerns, and
stakeholder approval. Do not claim legal compliance based only on code review.

TASK 6: PROTOTYPE / LIVE SYSTEM
-------------------------------
The checked-in Compose stack runs a local development prototype, not a public
production deployment. For a live deployment deliver the real HTTPS URL, date
and environment, supported test accounts (prefer temporary accounts), health
check evidence, and screenshots or a short demonstration record. Never publish
a secret demo password on a public paper/site. If only a local prototype is
available, label it clearly and provide local setup instructions. Include the
actual GitHub repository URL only after confirming the repository is published
and accessible; do not fabricate a URL.
