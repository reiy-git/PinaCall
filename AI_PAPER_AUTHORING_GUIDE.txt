PINACALL SAD PAPER: AI AUTHORING GUIDE
======================================

PURPOSE AND HOW TO USE THIS FILE
--------------------------------
This is an execution brief for an AI helping complete the Systems Analysis and
Design (SAD) project paper. Read it together with SYSTEM_GUIDE.md and
PROJECT_DOCUMENTATION_CHECKLIST.txt. The checklist gives the rubric; the system
guide maps the code; this file tells the AI exactly what to produce, what to
verify, and what to ask the team for.

Do the work section by section. Do not write unsupported claims to make a paper
look complete. Maintain a claim ledger with: claim; implementation source;
test/external evidence; status (implemented/tested/planned/team input); and
follow-up needed. If information is missing, write [TEAM INPUT REQUIRED: ...]
and ask the team for the exact item. Never invent people, dates, policy, URLs,
results, references, peer evaluations, approval, or detector scores.

SOURCE RULES
------------
1. Current application source, migrations, tests, package manifests, and Docker
   files establish what the prototype implements.
2. SYSTEM_GUIDE.md is the source map. Verify important/controversial claims in
   the named code; source wins if a summary differs.
3. PROJECT_DOCUMENTATION_CHECKLIST.txt is the required assignment rubric.
4. Course/instructor requirements, university policy, team records, and test or
   deployment outputs establish information the repository cannot prove.
5. Exclude generated dependencies and runtime output: api/vendor,
   frontend/node_modules, frontend/dist, caches, logs, local databases, and
   environment secrets. Never copy .env values, tokens, or real student data.

STATUS LANGUAGE
---------------
IMPLEMENTED means confirmed in current source.
TESTED means a command/manual test was actually executed and dated; identify the
command, environment, result, and evidence location.
PLANNED means proposed/not implemented.
TEAM INPUT means a human, instructor, institution, or operator must supply it.
A test method in source is not proof it was run or passed. A wireframe is not a
screenshot. Local Docker Compose is not a public deployment.

PINACALL TECHNICAL FACTS: KEEP THESE CONSISTENT
-----------------------------------------------
- Stack: Vue 3, TypeScript, Vite, Tailwind CSS 4; Laravel 13 JSON API using PHP
  8.4 in the current API image; PostgreSQL 15; Redis; Docker Compose.
- Local-only addresses: frontend http://localhost:5173; API
  http://localhost:8000/api; Laravel health endpoint http://localhost:8000/up.
- Roles: student, registrar, cashier, department_head, faculty, admin. The
  department head/dean is one department_head role in code. Do not draw a
  separate dean login/role unless the code is changed and verified.
- Student categories: new, transferee, irregular, old, shiftee, returnee.
- Main entities: User, Student, StudentApplication, Course, AcademicSection,
  SectionEnrollment, Enrollment, Clearance, DocumentRequest, ApiAccessToken.
- Student application approval and section roster enrollment are different
  events. Review may assign a section label; actual enrollment creates/updates
  roster/enrollment records later.
- Section enrollment checks open status, capacity, program/year match, student
  eligibility, and duplicate enrollment. Capacity-sensitive changes use a DB
  transaction/lock in SectionController.
- Grades: faculty writes are scoped to assigned-section active roster students;
  grade values currently validate from 1 through 5 to two decimals. When both
  midterm and final grades exist, code computes their arithmetic mean. Students
  see their own grades only when active, enrolled in the matching section, and
  the grade has been explicitly released. This is prototype logic, not an
  approved institutional grading policy.
- Clearance tracks cashier, library, dept, dean, guidance, registrar flags and
  remarks; overall status is cleared only if all six are approved.
- Document states are submitted, processing, ready_for_pickup, released, or
  rejected. Cashier sets paid/unpaid; registrar handles fulfillment. Fee values
  are hard-coded examples; there is no payment processor or official document
  issuance integration.
- Login and registration are public routes with named throttle middleware.
  Other API routes require a bearer token. Stored token is SHA-256 hashed and
  expires in eight hours. Frontend stores returned token in sessionStorage.
- Seeded users and academic records are local demonstration fixtures. The API
  container seeds only if the users table is empty. They are not production
  accounts or real student data.
- Current Dockerfiles are development-oriented: Vite development server and
  PHP built-in web server. Do not claim production readiness. No public live URL
  or verified GitHub URL is established by this guide.
- PortalWorkflowTest.php contains source tests for seed accounts, a role-scoped
  lifecycle, full/closed section rejection, enrollment reuse, grade visibility/
  release, and admin course/user authorization. Fresh execution is needed to
  claim tests pass.

REQUIRED PROJECT STORY
----------------------
Explain the problem as four specific pain points and connect each to a real
prototype workflow and a limit:
1. Physical enrollment queues: online student application, registrar review,
   eligibility and matching section enrollment. Limit: prototype, not a live
   university SIS/admissions process.
2. Clearance visits: one student clearance record tracks six office approvals
   and remarks. Limit: no verified institutional policy/evidence system or real
   payment/library integration.
3. Grade viewing: assigned faculty enter grades and explicitly release them;
   students see only eligible released records. Limit: grade scale/average and
   release authority need institutional approval; seed grades are not official.
4. Document requests: student requests, cashier marks payment, registrar
   advances fulfillment status. Limit: payment is simulated and no official
   document production/delivery system is integrated.

For every module in prose, say who uses it, what task they do, what screen and
API support it, what data is involved, what authorization applies, what success
looks like, what errors/empty states exist, and what remains prototype-only.
Use the roles and module map in SYSTEM_GUIDE.md. Do not infer modules from old
plans that are absent from current source.

TASK 1 - SDLC PLAN
==================
Produce the following subsections:
1. Selected SDLC and rationale. Iterative/Agile can fit a multi-role workflow
   that needs policy and user feedback. State that rationale does not prove
   historical sprints occurred.
2. Scope: four problems, six roles, document subsystem, in-scope behaviors, and
   non-goals (real payment, official transcript issuance, policy integration,
   legal/compliance certification, production operations unless verified).
3. Stakeholders: student, registrar, cashier, department head/dean, faculty,
   admin, institution IT/privacy contact, instructor/evaluator. Distinguish
   actual interview participants from proposed stakeholders.
4. Lifecycle stages: requirements, analysis, design, implementation, testing,
   feedback, deployment, maintenance. For each state objective, activities,
   inputs, output, owner, dependency, acceptance criterion, evidence path, and
   actual/proposed status/date.
5. Iteration plan. Possible future slices: auth/foundation; application and
   clearance; catalog/sections/rosters; grade/release; document/admin; security,
   accessibility, and deployment. Mark future unless team evidence proves they
   happened and supplies dates.
6. Change management: requirement approval, code/migration review, test/release
   process, policy owner, and version control. Do not claim a practice is used
   without evidence.
7. Risks/dependencies: approved admission/grade/fee rules; privacy and data
   security; secrets/hosting; section capacity concurrency; outage/backups;
   access-control defects; accessibility; missing live deployment/evidence.
8. Measurable acceptance criteria per role/workflow and unauthorized path.

Use an evidence table: stage/iteration | planned or actual | owner | date |
input | deliverable/evidence | exit test | status. Leave unknown cells marked
TEAM INPUT REQUIRED, not filled with assumptions.

- P6 Request/pay/process/release documents -> D5 Document requests.
- P7 Administer users/courses and view metrics -> D1/D3.
Label arrows with actual data. Distinguish actor, process, store, and denied/

B. USE CASE DIAGRAM
One boundary: PINACALL Academic Services Prototype. Actors and goals:
- Student: register/sign in; submit/view own application; request/view own
  clearance; browse/enroll eligible section; view released grades; request and
  track own document.
- Registrar: view application/student queue; review/approve/reject; release

- Cashier: update payment status and cashier clearance only.
- Department Head: department-scoped section/roster and dept/dean clearance

- Admin: view metrics/registry; maintain accounts/course catalog; permitted

C. ACTIVITY DIAGRAM

Branch for invalid input, duplicate pending application, rejection/hold, missing
clearance, closed section, capacity full, program/year mismatch. Show that

Optional second diagram: student requests document -> fee displayed -> cashier

TASK 3 - SYSTEM DESIGN
======================
A. STORYBOARD AND WIREFRAMES
Make two storyboards: (1) a student application -> review -> clearance ->
section flow, and (2) faculty grade/release or registrar document fulfillment.
Each frame must identify actor, screen, action, system response, decision/next
step, and error/empty path.

Produce labelled wireframes for:
1. Public landing, sign-in, student registration.
2. Student overview: application, clearance, course/grade, document states.
3. Registrar queue and application-review detail.
4. Cashier payment/clearance queue.
5. Department section/catalog/clearance workspace.
6. Faculty assigned-section roster and grade entry/release.
7. Admin metrics, user management, course catalog.
8. Document request form and status view.

For each screen include goal, data fields, primary/secondary action, role
permission, source/API, validation, loading/empty/error/success states, and
recovery action. Show desktop and phone layout. Specify keyboard order, focus,
labels, contrast, screen-reader semantics, and high-impact confirmation. These
are requirements until tested. Label each image as ACTUAL SCREENSHOT or PROPOSED
WIREFRAME. For screenshots note date, URL/environment, role, viewport, and never
show passwords or real student records.

B. ERD, DATA DICTIONARY, AND NORMALIZATION
Use every current migration, including later ALTER migrations. ERD should cover
users, students, student_applications, courses, academic_sections,
section_enrollments, enrollments, clearances, document_requests,
api_access_tokens. Add framework cache/jobs tables only if instructor requires.

Data dictionary columns: table/column, type/length, PK/FK/unique/null status,
meaning, allowed values, referenced table, migration source. State cardinality,
optional relationships, unique constraints, and delete behavior only as
migrations declare them. Do not describe initial table-creation migration as the
whole current schema.

Explain normalization from actual functional dependencies:
- 1NF: atomic values/no repeating groups; discuss submitted_documents array/JSON
  and whether a separate document table is required for query/report needs.
- 2NF: full dependency on key; analyze section_enrollments pair and its status/
  enrolled_at fields.
- 3NF: non-key facts depend on key, not transitively. Evaluate duplicated
  User/Student name/email and stored computed grade/remarks; explain dependency
  and tradeoff rather than claiming violation without analysis.
- Explain SectionEnrollment as roster pivot vs Enrollment as academic result.
- Describe nullable section links/legacy compatibility and identify which rules
  are database constraints vs controller validation.

TASK 4 - TESTING PLAN
=====================
Describe strategy by level, scope/risk, synthetic test data, setup/teardown,
environment, entry/exit criteria, defect severity, responsible tester, and
report location. `make test` intends in-memory SQLite and array/sync session,
cache, and queue. Confirm current command. Never point RefreshDatabase tests at
persistent Compose PostgreSQL or use destructive resets on needed data.

Every test case fields: ID | level | requirement | preconditions | test data |
steps | expected | actual | status/date | tester | command/environment |
evidence path. Use NOT RUN until executed. Source test code is not a pass result.

Existing cases to map to requirements and freshly execute in isolation:
- Seed contains demo logins for every role and faculty has sections/enrollments.
- Full role-scoped lifecycle: application, registrar review, clearance, roster,
  grade entry/release, document payment/fulfillment, admin stats authorization.
- Reject full/closed section enrollment.
- Reuse an existing course enrollment without duplicating it during section
  assignment.
- Student grade visibility requires active student and explicit release.
- Only admin can create/update users/courses; duplicate course code rejected;
  inactive account login denied.

Explicit gaps to mark missing unless verified in newer source: protected route
without token; expired/revoked/inactive token; cross-student IDOR for each
resource; faculty writing/releasing another faculty's roster grade; grade bounds,
precision and exponent string; unauthorized clearance office; unpaid/illegal
document transition; CORS allowed/disallowed origin; service restart and data
persistence; responsive/keyboard acceptance; performance.

Proposed test cases (leave actual result NOT RUN until executed):
| ID | Level | Scenario | Expected result |

| UT-02 | Unit | Grade out of range, >2 decimals, exponent notation | API rejects request. |

concurrency, duration, numerical target, raw output, and resource measurements.

impact, current code control, test steps, observed result, severity, remediation
owner, retest, residual risk. At least cover SQL injection, brute force/rate
limiting, and broken access control/IDOR. CORS is not authentication. Do not
claim security certification.

TASK 5 - ETHICAL EVALUATION
===========================
Ask which principles/theories the class requires. For each principle state its
definition, affected stakeholder, relevant PINACALL data/function, benefit,
potential harm, code/policy evidence, gap, mitigation, responsible owner, and
residual risk. Discuss competing interests, not only benefits.

Cover at least:
- Privacy/confidentiality of names, email, student number, applications,
  grades, emergency contacts, clearances, documents; minimize collection, limit
  purpose/access, notice/consent, retention/deletion, backups, breaches, tokens.
- Fairness/non-discrimination across six student categories, consistent review,
  appeals, disabilities, language, device and connectivity access.
- Accuracy/nonmaleficence: demo grades, calculated results, fees, and statuses
  could harm someone if treated as official; require clear labels and human
  verification against approved policy.
- Transparency/autonomy: explain required information, who can see it, decision
  rules, grade release, fees, and correction/appeal paths.
- Accountability: identify office/owner for actions, corrections and incidents;
  current admin logs are not a complete academic audit system.
- Accessibility/inclusion: test keyboard/focus, contrast, labels, screen reader,
  mobile/responsive and low bandwidth; do not claim WCAG conformance without
  evidence.
- Professional integrity: accurate implemented/planned distinction, truthful
  AI disclosure under course rules, citations, data protection.

Request the applicable university privacy policy and jurisdiction before making
legal-compliance claims. Code inspection alone cannot establish compliance.
